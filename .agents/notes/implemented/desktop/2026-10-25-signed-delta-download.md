# 签名差分下载：还原完整载荷后沿用原安装生命周期

- 日期：2026-10-25
- 状态：已实施；2026-10-26 云端四平台开发验收通过，未正式发布或完成真实跨版本原位升级
- 范围：Windows NSIS、macOS x64/arm64 app archive；Linux deb 继续手动更新

## 背景与保留边界

现有[更新器](../../../../desktop/src-tauri/src/updater.rs)是签名整包下载/覆盖，不是二进制差分。[原信任锚](../../implemented/desktop/2026-10-24-first-signed-release-trust-anchor.md)与[后台生命周期](../../implemented/desktop/2026-10-22-diagnostics-and-update-lifecycle.md)继续有效：固定仓库、公钥与受签名版本；Demo/普通网页不更新，用户确认后才下载；完整载荷验证后才能暂停后台；安装失败沿原恢复路径，不二次下载/重装。

用户明确选取真正差分，并要求软件编译只在 GitHub Actions 进行。新增依赖的锁文件解析、测试夹具生成及所有构建/产品检查也在云端完成，不在本机回退编译。

## 选择

差分只优化**传输**：用 BSDIFF40/qbsdiff 1.4.4 对完整签名安装器或 app.tar.gz 做差分，不修补运行目录或已安装文件。先验证补丁自己的原公钥签名和目标受签名版本，再有界还原；还原结果必须通过原完整包签名/版本验证，之后仍由官方 Tauri install 再验证并安装。不引入新公钥或自写密码学。

保持旧 `version/platforms/url/signature` 与三个原平台条目不变；新增可选顶层 `deltas`，按完整目标键分别列出最多一个基线。描述符为 `format=bsdiff40`，包括 base/target version、SHA256、大小、原整包 URL/signature 以及补丁 URL/signature/SHA256/大小。SHA与描述符不是信任根；未知/损坏/不兼容字段不得阻断正常完整包。

只在完整平台、包类型、当前版本及精确基础包摘要匹配时选补丁，补丁必须小于完整包的80%。没有缓存不从运行文件拼基线、不为差分先下载旧整包；第一次通常仍走整包。下载、补丁验签、预审、还原或最终包验签失败，最多一次回退原候选整包，且全部发生在 Artifact.download 返回已验证完整 bytes 之前。安装阶段的任何错误都不能触发二次安装。

## 资源与缓存

清单实际读取上限1MiB，整包/基线64MiB、补丁32MiB；每跳只允许 HTTPS 及明确的官方 GitHub Release CDN，最多五跳，不携应用认证头或输出签名重定向地址。完整回退使用自身上限与原候选官方签名，不以不可信差分元数据的目标摘要/长度为门槛。

qbsdiff 解码器本身不提供完整预算。必须先检查 BSDIFF40 非负长度与 checked 算术，流式预审解压控制量、控制记录/连续零进展、来源区间和总输出，预审差分/extra量与实际目标一致，再用成熟库还原。字节/记录预算及合作式 deadline 不应误称为可杀死阻塞线程的硬 CPU 超时；不能用 timeout(spawn_blocking) 或 catch_unwind 代替预防，release 的 panic=abort 仍在。

缓存只在确认安装后的下载路径使用，位于固定版本化 app cache 子目录；文件名由白名单完整平台/包类型、版本和摘要构造。按同一已打开对象读取、哈希和使用，拒绝链接/reparse/nonregular；独占锁失败只退化无缓存。已验签目标在进入 Windows 可能 exit 的安装前，以同目录独占临时文件完整写入并原子提交。最多保留两个64MiB整包；初案预算192MiB，实施时写前腾至一份，使缓存目录含暂存的包数据峰值收紧至128MiB，不包括官方安装器自身临时目录。只清理自有命名且不在使用的条目，不能扫用户文件；缓存不可用不使本来有效的安装失败。

## 发布与兼容

发布云端先验证公开旧基线与新完整包的原公钥/受签名版本，再生成并逐字节复原验证收益，使用锁定 Tauri signer 的 `--app-version` 对补丁签名，随后仍以原公钥验证补丁及完整载荷。没有可信旧基线或不省流量时只发完整包；补丁签名失败不能发布半成品。只在未来明确发布 tag 流程使用已有签名 secret，本次开发验证不读取生产私钥、不发布 Release。

原13资产基线、三个正式完整载荷、版本/URL/inline签名及摘要门槛不放宽；存在补丁时只增加经过规范校验的补丁和签名。旧客户端忽略顶层扩展，继续下载相同完整载荷。官方签名绑定载荷和版本，不单独认证架构；完整目标选择、精确 URL/signature 配对及发布架构检查继续负责平台边界，不另起签名协议迁移。

## 实际考虑的替代与代价

- 只做整包续传：实现较小，但不满足用户明确要求的真正差分。
- 原位修补已安装目录：Windows锁文件、macOS archive/签名及回滚边界更复杂，会替换现有安装器责任，本轮不选。
- 仅验最终包再处理未签补丁：虽可防止错误安装，却把未认证压缩输入交给解码器，因此改为补丁先签名、完整包再签名。
- 自写补丁算法或验签：维护和安全成本高，使用成熟库/CLI与官方 updater。

平台文件层选用已锁 `rustix 1.1.5` 的安全 dirfd 包装与 `windows-sys 0.61.2` 官方 Wdk/Win32 绑定，取代手写 errno/目录枚举/NT ABI；仅保留有界变长结构调用的小 FFI 边界。实际比较了 [cap-std](https://docs.rs/cap-std/4.0.3/cap_std/fs/struct.Dir.html)、[cap-fs-ext](https://docs.rs/cap-fs-ext/4.0.3/cap_fs_ext/trait.OpenOptionsFollowExt.html)、[cap-tempfile](https://docs.rs/cap-tempfile/4.0.3/cap_tempfile/struct.TempFile.html)：相对目录能力可简化路径，但 nofollow 仍须逐组件，TempFile::replace 会覆盖且没有等价 no-clobber 公共接口；已锁 tempfile 的按路径 persist_noclobber 也不保证提交原已开对象。因此本轮不引入整套 capability 依赖，使用成熟系统绑定并验证发布对象的打开句柄身份，不把少依赖作为拒用成熟库的理由。缓存并非同UID恶意进程不可篡改的信任根，最终签名与重读摘要仍是安全门槛。

代价是额外缓存、发布步骤及第三方依赖。压缩签名包的差分不保证总有收益；预算/收益不满足就保留整包。真实跨版本签名发行、Windows/macOS原位升级与失败回滚仍须单独记录实际证据，不能由纯 fixture 或开发包宣称通过。
